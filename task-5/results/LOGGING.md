# Обоснование способа отправки и хранения логов

## Выбранное решение

Для централизованного логирования выбран стек ELK:

```text
Приложения → stdout/stderr в JSON
        ↓
Filebeat
        ↓
Logstash
        ↓
Elasticsearch
        ↓
Kibana
```

## Почему ELK

У TradeWare одновременно остаётся существующее Java/WildFly-приложение и появляются новые сервисы на Spring Boot и Spring Batch. Поэтому нужен единый способ собирать, нормализовать и искать логи из разных источников.

1. **Filebeat** — лёгкий агент доставки логов. Его удобно использовать для контейнерных логов и файловых логов существующих компонентов.
2. **Logstash** — конвейер обработки логов. Он позволяет привести старые текстовые и новые JSON-логи к единой схеме, отфильтровать технический шум и добавить служебные поля.
3. **Elasticsearch** — хранилище и поисковый движок для индексированных документов. Он подходит для расследования по `file_id`, `job_execution_id`, `trace_id` и `error_code`.
4. **Kibana** — интерфейс поиска и визуализации. Инженеру не нужно подключаться к каждой VM или Pod отдельно.

Если корпоративные ограничения по лицензии Elastic не позволяют использовать Elasticsearch и Kibana, близкой по возможностям альтернативой будет OpenSearch + OpenSearch Dashboards.

## Способ отправки

Новые контейнеризированные приложения пишут **структурированный JSON в `stdout/stderr`**. Приложение не должно самостоятельно управлять файлами логов, их ротацией и доставкой.

Filebeat собирает контейнерные логи и файлы существующего приложения и передаёт их в Logstash. Такой подход отделяет бизнес-логику от доставки логов: временная недоступность Elasticsearch не должна превращать пользовательский запрос в ошибку только потому, что запись не удалось немедленно отправить в хранилище логов.

## Минимальная схема события

```json
{
  "@timestamp": "2026-09-06T16:20:15.123Z",
  "level": "INFO",
  "service": "report-batch-worker",
  "environment": "prod",
  "event": "chunk_completed",
  "trace_id": "...",
  "span_id": "...",
  "file_id": "f-12345",
  "job_execution_id": 9123,
  "step": "enrich-and-write",
  "rows_read": 500,
  "rows_written": 500,
  "duration_ms": 820
}
```

Названия полей оставлены на английском, потому что это машинный контракт логирования, а не пользовательский текст.

Для ошибки дополнительно записываются `error_code`, `exception_class`, `message`, трассировка стека и номер повторной попытки.

## Уровни логирования

- `INFO` — начало и завершение Job/Step, агрегированные счётчики;
- `WARN` — восстанавливаемая ошибка, повторная попытка, допустимый пропуск, подозрительное состояние;
- `ERROR` — неисправимая ошибка Step/Job;
- `DEBUG` и `TRACE` — только временно для диагностики, постоянно в промышленной среде не включаются.

## Что запрещено логировать

- пароли и секреты;
- токены доступа и обновления;
- строки подключения с учётными данными;
- полное содержимое CSV-файла;
- персональные данные, которые не нужны для диагностики;
- платёжные реквизиты.

Вместо содержимого строки следует логировать `file_id`, контрольную сумму, номер строки и стабильный `error_code`.

## Индексы и схема полей

Для индексов Elasticsearch использовать явное сопоставление полей, а не бесконтрольное динамическое создание полей.

Базовые поля:

- `service`, `environment`, `level`, `event`, `error_code`, `file_id`, `trace_id` — тип `keyword`;
- `message` и трассировка стека — тип `text`;
- `duration_ms` и счётчики строк — числовые типы;
- `@timestamp` — тип `date`.

## Управление жизненным циклом индексов

Использовать **Index Lifecycle Management (ILM)**:

1. горячая стадия — свежие индексы для оперативных расследований;
2. ролловер по размеру первичного шарда, возрасту или общему размеру;
3. тёплая и холодная стадии — если это оправдано стоимостью хранения;
4. удаление после согласованного срока хранения.

Для обычных технических логов разумная начальная гипотеза — около 30 дней. Аудитные и журналы безопасности должны храниться в соответствии с требованиями ИБ и законодательства. Конкретные сроки утверждает владелец данных совместно с ИБ.

## Корреляция с метриками и трассировкой

В JSON-лог включаются `trace_id` и `span_id`. При инциденте инженер действует так:

1. получает оповещение от Alertmanager;
2. смотрит метрики в Grafana;
3. ищет `file_id` или `trace_id` в Kibana;
4. по тому же `trace_id` открывает распределённую трассировку в Jaeger.

Так метрики помогают заметить проблему, логи дают технические детали, а трассировка показывает полный путь операции между компонентами.
