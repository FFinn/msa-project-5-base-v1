# Задание 4. Пакетная обработка TradeWare с использованием Spring Batch

В этом задании проанализирован текущий процесс загрузки отчётов TradeWare и предложена целевая архитектура, в которой тяжёлая обработка вынесена из пользовательского запроса в отдельный асинхронный компонент на Spring Batch.

## Результаты

- `ADR-003-spring-batch-etl.md` — архитектурное решение с требованиями, альтернативами, последствиями и рисками;
- `c4-to-be.puml` — исходник контейнерной C4-диаграммы целевого состояния;
- `c4-to-be.drawio` — редактируемая диаграмма Draw.io;
- `c4-to-be.png` — экспорт диаграммы для просмотра в репозитории;
- `poc/` — локальный демонстрационный прототип Spring Batch.

## Основная идея решения

Текущий монолит не должен продолжать синхронно обрабатывать большой CSV-файл внутри пользовательского запроса. Приём файла и его тяжёлая обработка разделяются:

1. сотрудник склада загружает CSV через ERP-интерфейс;
2. отдельный сервис приёма выполняет быструю первичную проверку;
3. исходный файл сохраняется в Google Cloud Storage;
4. пользователю возвращается подтверждение приёма и идентификатор загрузки;
5. задание помещается в очередь;
6. отдельный обработчик Spring Batch читает файл, проверяет и обогащает данные, затем записывает результат в PostgreSQL порциями;
7. техническое состояние Job и Step сохраняется в `JobRepository`;
8. пользователь получает состояние обработки из отдельного хранилища прикладных статусов.

Так тяжёлая работа перестаёт блокировать пользовательский API, а очередь позволяет сглаживать пиковые 100–150 параллельных загрузок.

## Почему Spring Batch

Spring Batch подходит для этого процесса, потому что здесь нужна именно управляемая пакетная обработка:

- чтение большого файла без загрузки всего содержимого в память;
- обработка порциями;
- транзакционная запись порциями;
- повторные попытки для временных ошибок;
- контролируемый пропуск отдельных некорректных записей;
- сохранение контрольных точек и продолжение после сбоя;
- естественная интеграция с Java/Spring-экосистемой TradeWare.

При этом Spring Batch не решает сам по себе задачу приёма 100–150 загрузок. Для этого в архитектуре используется очередь и ограниченное число обработчиков, которое масштабируется с учётом возможностей PostgreSQL.

## Производительность

Требование бизнеса: **среднее время обработки отчёта на 2 000 строк — не более 30 секунд**.

Это значение нельзя гарантировать только выбором фреймворка. Его необходимо подтвердить нагрузочным тестированием на данных, близких к промышленным. В ходе теста подбираются:

- размер порции данных;
- число параллельных обработчиков;
- настройки пула соединений;
- массовая запись в PostgreSQL;
- лимиты CPU и памяти.

Подробности приведены в ADR-003.

## Альтернативы

Также рассмотрены:

- Apache Airflow — лучше подходит для сложных графов зависимостей и координации разнородных внешних систем;
- Spring Cloud Data Flow — полезен как следующий уровень централизованного управления множеством Spring Batch Job;
- Kubernetes Job/CronJob — подходит как среда запуска, но не заменяет механизмы Spring Batch;
- Apache Spark и Google Cloud Dataflow — оправданы при существенно больших объёмах и распределённых вычислениях.

Для текущего этапа выбран Spring Batch как наиболее близкий к характеру задачи и существующему стеку команды.
