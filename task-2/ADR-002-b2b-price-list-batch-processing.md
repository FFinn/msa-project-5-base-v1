# ADR-002. Выбор технологии для ежедневного формирования B2B-прайс-листов

- **Статус:** Accepted
- **Дата:** 2026-09-07
- **Контекст:** проектная работа спринта 5, Task 2

## 1. Контекст

Онлайн-магазину необходимо **каждое утро ровно в 06:00** формировать кастомные CSV/XLS-прайс-листы для B2B-клиентов на основе актуальных данных PostgreSQL.

Исходные таблицы:

- `products` — ~5 000–10 000 строк;
- `categories` — ~50–200 строк;
- `clients` — ~100–500 строк;
- `client_prices` — ~10 000–20 000 строк.

Итоговая выгрузка содержит порядка **5 000–10 000 строк**. Дополнительной сложной логики трансформации, ветвлений, ML или распределённых вычислений не требуется. Инфраструктура магазина уже построена как облачная микросервисная среда.

Главная задача — надёжно запускать одну контейнеризированную экспортную операцию по расписанию, связать данные SQL-запросом и опубликовать готовые файлы.

## 2. Decision drivers

При выборе решения учитываются:

1. наличие запуска по CRON-расписанию ровно в 06:00;
2. минимальная сложность реализации простой SQL-выгрузки;
3. минимальное постоянное потребление ресурсов;
4. достаточная масштабируемость для текущего и умеренно растущего объёма;
5. простота развёртывания в существующей облачной Kubernetes-инфраструктуре;
6. интеграция с централизованными логами и мониторингом;
7. предсказуемое поведение при сбоях и повторных запусках;
8. отсутствие избыточной платформенной сложности для одного простого batch-процесса.

## 3. Рассмотренные варианты

> В колонке **K8s Job** рассматривается связка **Kubernetes CronJob → Job → Pod**, потому что сам `Job` не содержит расписания, а `CronJob` создаёт `Job` по CRON.

| Критерий | Spring Batch | Apache Airflow | K8s Job / CronJob | Spark |
|---|---|---|---|---|
| Наличие CRON-расписания | Сам Spring Batch — нет; нужен Spring Scheduler, Quartz, CronJob или SCDF | Да, встроенное расписание DAG | **Да, встроено в CronJob** | Нет, нужен внешний scheduler/orchestrator |
| Сложность реализации логики обработки | Средняя: Job/Step/Reader/Writer для одной SQL-выгрузки избыточны | Средняя/высокая: DAG и инфраструктура Airflow избыточны для одного шага | **Низкая**: один контейнер выполняет SQL и формирует файлы | Высокая и неоправданная для 5–10 тыс. строк |
| Ресурсоёмкость | Средняя: JVM + batch-приложение | Высокая: scheduler, webserver, metadata DB, executor/workers | **Низкая**: pod существует только во время выполнения | Высокая: driver/executors/cluster overhead |
| Масштабируемость | Хорошая; partitioning требует дополнительной настройки | Высокая для множества DAG/tasks | **Достаточная для кейса**; можно увеличить resources или partition/parallelism при росте | Очень высокая, но избыточная для текущего объёма |
| Развёртывание в облаке и интеграция с микросервисами | Хорошо для Java/Spring-экосистемы | Хорошо, но требует отдельной платформы | **Отлично**: нативный объект Kubernetes в уже существующей облачной среде | Сложнее и дороже в эксплуатации |
| Интеграция с логированием и мониторингом | Micrometer/Actuator + централизованные логи | Встроенный UI + внешние метрики/логи | **Хорошая**: stdout/stderr, Kubernetes events, Prometheus/Grafana, ELK/OpenSearch | Хорошая, но нужен отдельный monitoring stack |

## 4. Решение

Выбрать **Kubernetes CronJob**, который каждый день в 06:00 создаёт `Job`, а тот запускает одноразовый `Pod` с контейнером `price-list-exporter`.

### Основные параметры CronJob

- `schedule: "0 6 * * *"`;
- явный `timeZone` с бизнес-часовым поясом;
- `concurrencyPolicy: Forbid`, чтобы новый ежедневный запуск не пересекался с предыдущим;
- `startingDeadlineSeconds` для допустимого запоздалого запуска после временной недоступности control plane;
- `backoffLimit` для ограниченного числа повторных попыток;
- `successfulJobsHistoryLimit` и `failedJobsHistoryLimit`;
- `resources.requests/limits`;
- credentials БД через `Secret`/облачный Secret Manager;
- непривилегированный runtime и минимальный `ServiceAccount`.

## 5. Логика формирования прайс-листов

Экспортёр открывает **read-only** соединение с PostgreSQL и выполняет SQL с JOIN по `products`, `categories`, `clients`, `client_prices`.

Чтобы избежать N+1-запросов для 100–500 клиентов, предпочтительно получить данные одним потоковым запросом, включающим `client_id`, и отсортировать результат, например, по `client_id`, `category_id`, `product_id`. Экспортёр последовательно формирует отдельный файл каждого клиента, переключая writer при изменении `client_id`.

Для CSV используется потоковая запись. Для XLSX следует использовать streaming/write-only API библиотеки, чтобы не удерживать весь workbook в памяти.

Файл сначала формируется под временным именем. Только после успешного завершения он публикуется под финальным детерминированным ключом, например:

`price-lists/<run-date>/<client-id>/price-list.csv`

Это защищает потребителя от чтения частично записанного файла и делает повторный запуск за ту же дату идемпотентным.

## 6. Хранение результата

В облачной среде итоговые CSV/XLS-файлы следует размещать в объектном хранилище (например, GCS или S3-compatible storage), а не на локальном filesystem Pod.

Преимущества:

- файлы переживают завершение Pod;
- можно настроить lifecycle/retention/versioning;
- доступ можно ограничить отдельным bucket/prefix;
- B2B-система может отдавать клиенту signed URL или предоставлять файл через существующий API.

## 7. Отказоустойчивость и повторный запуск

- `concurrencyPolicy: Forbid` исключает одновременное выполнение двух ежедневных выгрузок;
- `backoffLimit` ограничивает повторные попытки упавшего Job;
- ненулевой exit code контейнера переводит Job в ошибочное состояние;
- детерминированный ключ результата делает повторную обработку одной даты безопасной;
- публикация только после полного формирования файла не допускает появления частичных результатов;
- должен быть предусмотрен runbook для ручного запуска Job за конкретную дату.

## 8. Наблюдаемость

Контейнер пишет структурированные логи в `stdout/stderr`; они собираются существующей системой централизованного логирования.

Минимально контролируются:

- статус Job (`Succeeded` / `Failed`);
- длительность выполнения;
- количество экспортированных строк и клиентов;
- размер файлов;
- время последнего успешного запуска;
- факт наличия всех ожидаемых файлов к контрольному времени.

Для инфраструктурных метрик подходят Prometheus/Grafana, для логов — ELK/OpenSearch или существующий централизованный log stack.

## 9. Почему отклонены альтернативы

### Spring Batch

Технически подходит и даёт chunk-oriented processing, restartability и retry. Однако для одной простой ежедневной SQL-выгрузки потребует отдельного Java batch-приложения и внешнего scheduler. Его преимущества не окупают дополнительную сложность текущего кейса.

### Apache Airflow

Подходит для сложных DAG, зависимостей, ветвлений и множества разнородных интеграций. Здесь pipeline состоит фактически из одной операции, поэтому отдельные scheduler, webserver, Metadata DB и executor являются неоправданным overhead.

### Apache Spark

Spark предназначен для распределённой обработки больших объёмов данных. Набор в 5–10 тыс. строк и простая SQL-операция не требуют распределённого compute engine.

## 10. Последствия решения

### Положительные

- минимальная архитектурная и эксплуатационная сложность;
- ресурсы расходуются только во время выполнения;
- решение нативно встраивается в Kubernetes;
- легко контейнеризовать и перенести между облачными средами;
- стандартные Kubernetes-механизмы дают scheduling, retry и контроль пересекающихся запусков;
- решение достаточно для текущего объёма и имеет понятный путь масштабирования.

### Ограничения

- CronJob не является полноценным workflow-оркестратором;
- сложные зависимости и ветвления придётся реализовывать в приложении либо мигрировать на Airflow/SCDF;
- при существенном росте вычислительной сложности может потребоваться partitioning или специализированный processing engine.

## 11. Критерии пересмотра ADR

Решение следует пересмотреть, если:

- появится несколько взаимозависимых batch-процессов;
- появятся сложные ветвления и внешние интеграции;
- одна выгрузка перестанет укладываться в допустимое окно даже после оптимизации SQL и ресурсов Pod;
- объёмы вырастут на порядки и потребуют распределённой обработки.
