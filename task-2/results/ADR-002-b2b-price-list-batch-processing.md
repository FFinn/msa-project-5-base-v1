# ADR-002. Выбор решения для ежедневного формирования B2B-прайс-листов

- **Статус:** принято
- **Автор:** Александр Вафин
- **Дата:** 2026-09-07
- **Контекст:** проектная работа 5 спринта, задание 2

## 1. Контекст

Каждое утро в 06:00 онлайн-магазин должен формировать индивидуальные CSV/XLS-прайс-листы для B2B-клиентов.

Исходные данные находятся в PostgreSQL:

- `products` — примерно 5 000–10 000 строк;
- `categories` — примерно 50–200 строк;
- `clients` — примерно 100–500 строк;
- `client_prices` — примерно 10 000–20 000 строк.

Одна итоговая выгрузка содержит порядка 5 000–10 000 строк. Дополнительных преобразований, сложных ветвлений или распределённых вычислений не требуется: нужно связать данные SQL-запросом и сформировать файлы.

Инфраструктура магазина уже облачная и микросервисная, поэтому решение должно естественно в неё встраиваться и не создавать отдельную тяжёлую платформу без необходимости.

## 2. Требования

### 2.1. Функциональные требования

| № | Требование |
|---|---|
| **ФТ-01** | Система должна запускать формирование прайс-листов ежедневно ровно в 06:00. |
| **ФТ-02** | Система должна читать данные `products`, `categories`, `clients`, `client_prices` из PostgreSQL. |
| **ФТ-03** | Данные должны связываться одним или небольшим числом SQL-запросов без N+1-запросов по клиентам. |
| **ФТ-04** | Для каждого B2B-клиента должен формироваться отдельный CSV и при необходимости XLSX. |
| **ФТ-05** | Готовые файлы должны публиковаться в объектное хранилище только после полного успешного формирования. |
| **ФТ-06** | Повторный запуск за одну дату не должен создавать неконтролируемые дубликаты или частичные результаты. |

### 2.2. Нефункциональные требования

| № | Требование | FURPS+ |
|---|---|---|
| **НФТ-01** | Решение должно быть простым в сопровождении и соответствовать небольшой сложности задачи. | S |
| **НФТ-02** | Решение должно разворачиваться в существующей облачной Kubernetes-инфраструктуре. | + |
| **НФТ-03** | При сбое должны быть ограниченные повторные попытки и понятный итоговый статус выполнения. | R |
| **НФТ-04** | Новый ежедневный запуск не должен пересекаться с предыдущим незавершённым плановым запуском. | R |
| **НФТ-05** | Потребление CPU и памяти должно быть ограничено настройками Kubernetes. | P |
| **НФТ-06** | Логи и основные показатели выполнения должны передаваться в централизованную систему наблюдаемости. | S |

### 2.3. Основной сценарий использования

| UC-ID | Название | Основной поток | Альтернативный поток | Связанные требования |
|---|---|---|---|---|
| **UC-01** | Ежедневное формирование прайс-листов | 06:00 → запуск Job → чтение PostgreSQL → формирование файлов → публикация в объектное хранилище → успешное завершение | ошибка → ограниченные повторные запуски → статус `Failed` и оповещение | ФТ-01…ФТ-06, НФТ-01…НФТ-06 |

## 3. Сравнение вариантов

| Критерий | Spring Batch | Apache Airflow | Kubernetes Job/CronJob | Apache Spark |
|---|---|---|---|---|
| Запуск по расписанию | Требуется Spring Scheduler, Quartz, Kubernetes CronJob или внешний оркестратор | Есть собственное расписание DAG | **Есть штатно через CronJob** | Нужен внешний планировщик |
| Сложность реализации текущей логики | Средняя: потребуется отдельное Spring Batch-приложение | Высокая относительно задачи: нужен Airflow и DAG | **Низкая: один контейнер и один CronJob** | Высокая и неоправданная |
| Ресурсоёмкость решения | Средняя | Высокая: отдельная платформа | **Низкая: ресурсы потребляются только во время Job** | Высокая |
| Масштабирование | Хорошее, но потребует настройки Spring Batch | Хорошее, но требует инфраструктуры Airflow | **Достаточное для текущего объёма, масштабируется средствами Kubernetes** | Очень хорошее, но избыточное |
| Развёртывание в облаке | Удобно в контейнере, но нужен отдельный механизм запуска | Требуется Airflow или управляемый сервис | **Наиболее естественно для Kubernetes-инфраструктуры** | Требуется Spark-кластер или управляемый сервис |
| Мониторинг и логирование | Micrometer/Actuator + внешние системы | Богатый встроенный интерфейс | **Kubernetes + Prometheus/Grafana + централизованные логи** | Нужен отдельный контур наблюдаемости |

## 4. Рассмотренные альтернативы

### 4.1. Spring Batch

Spring Batch хорошо подходит для сложной пакетной обработки: чтения порциями, преобразований, повторных попыток и продолжения после сбоя. Но в этой задаче нет сложной логики обработки. Фактически требуется один SQL-запрос и формирование файлов. Введение Spring Batch увеличит объём кода и сопровождения без заметной пользы.

### 4.2. Apache Airflow

Airflow отлично управляет многошаговыми процессами с зависимостями и внешними интеграциями. Здесь же нет DAG из нескольких самостоятельных шагов. Ради одной простой ежедневной операции придётся сопровождать отдельную платформу, что противоречит НФТ-01.

### 4.3. Apache Spark

Spark рассчитан на распределённые вычисления над большими наборами данных. Объём 5 000–10 000 строк в итоговой выгрузке и простая SQL-логика не оправдывают его использование.

## 5. Решение

Выбрать **Kubernetes CronJob**.

CronJob в 06:00 создаёт Kubernetes Job, который запускает один Pod с приложением экспорта. Приложение читает PostgreSQL потоково, формирует отдельные файлы по клиентам и публикует их в объектное хранилище.

Это решение выбрано не потому, что CronJob «мощнее» остальных вариантов, а потому, что он лучше соответствует фактической сложности задачи. Здесь важнее простота, предсказуемость и небольшие эксплуатационные затраты.

## 6. Как решение закрывает требования

- **ФТ-01:** `schedule: "0 6 * * *"` и явный `timeZone` задают ежедневный запуск.
- **ФТ-02, ФТ-03:** приложение выполняет потоковый SQL-запрос с `JOIN` и сортировкой по `client_id`.
- **ФТ-04:** при смене `client_id` приложение завершает файл текущего клиента и начинает следующий.
- **ФТ-05:** файл сначала формируется под временным именем, после чего публикуется итоговый объект.
- **ФТ-06:** используется детерминированная структура ключей по дате и клиенту.
- **НФТ-03:** `backoffLimit` ограничивает число повторных запусков.
- **НФТ-04:** `concurrencyPolicy: Forbid` не позволяет очередному плановому запуску пересечься с предыдущим.
- **НФТ-05:** `resources.requests/limits` ограничивают CPU и память.
- **НФТ-06:** приложение пишет структурированные логи в `stdout/stderr`, а состояние Job контролируется средствами Kubernetes и системы мониторинга.

## 7. Архитектура выполнения

```text
Kubernetes CronJob
        ↓ 06:00
Kubernetes Job
        ↓
Pod с price-list-exporter
        ↓
PostgreSQL → потоковый SQL/JOIN
        ↓
CSV/XLSX по клиентам
        ↓
Объектное хранилище
```

На контекстной C4-диаграмме Kubernetes не выделяется как отдельная бизнес-система, потому что это инфраструктура. На контейнерной диаграмме показано, что модуль формирования прайс-листов выполняется как CronJob → Job → Pod.

## 8. Положительные последствия

- минимальная платформенная сложность;
- решение использует уже существующую Kubernetes-инфраструктуру;
- ресурсы потребляются только во время выполнения;
- легко задать ограничения CPU и памяти;
- понятная модель повторных запусков;
- отсутствует отдельный постоянно работающий оркестратор;
- решение легко проверить локально и перенести в облако.

## 9. Отрицательные и нейтральные последствия

- CronJob не подходит для сложных графов зависимостей;
- при появлении ветвлений, нескольких зависимых шагов и сложной логики восстановления текущий вариант придётся пересмотреть;
- наблюдаемость не такая богатая, как в Airflow, поэтому метрики, логи и оповещения нужно подключать отдельно;
- прикладная идемпотентность формирования файлов остаётся ответственностью приложения экспорта.

## 10. Риски и ограничения

1. Необходимо явно задать часовой пояс и проверить его поддержку используемой версией Kubernetes.
2. `concurrencyPolicy: Forbid` относится к плановым запускам конкретного CronJob и не является общей блокировкой вручную созданных Job.
3. Файлы нельзя хранить только во внутренней файловой системе Pod, так как Pod временный.
4. Нужно использовать пользователя PostgreSQL с правами только на чтение.
5. Индивидуальные файлы клиентов должны быть изолированы на уровне ключей и прав доступа объектного хранилища.
6. До промышленного запуска требуется проверить время выполнения и память на реальном объёме данных.

## 11. Когда решение стоит пересмотреть

ADR следует пересмотреть, если процесс перестанет быть одной простой ежедневной операцией: появятся сложные зависимости, ветвления, десятки шагов, необходимость повторного запуска отдельных стадий или централизованного управления множеством подобных процессов. В таком случае Apache Airflow или Spring Batch могут стать более подходящими вариантами.
