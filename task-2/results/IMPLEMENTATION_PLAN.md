# Верхнеуровневый план имплементации Task 2

## 1. Подготовка экспортёра

1. Создать небольшое stateless-приложение `price-list-exporter`.
2. Получать параметры подключения к PostgreSQL только из переменных окружения/Secret.
3. Использовать read-only пользователя БД.
4. Реализовать SQL с JOIN по `products`, `categories`, `clients`, `client_prices`.
5. Читать результат потоково/cursor-подходом и писать CSV без накопления всех строк в памяти.
6. Для каждого файла использовать детерминированное имя, например `price-list-<client-id>-2026-09-06.csv`.
7. Записывать сначала во временное имя, а после успешного завершения атомарно публиковать/загружать финальный объект, чтобы потребитель не увидел частичный файл.
8. Повторный запуск за ту же дату сделать идемпотентным: либо перезаписывать объект с тем же ключом, либо писать версионированный объект и атомарно обновлять указатель на актуальную версию.

## 2. Контейнеризация

1. Подготовить Dockerfile с минимальным runtime-образом.
2. Запускать процесс от непривилегированного пользователя.
3. Добавить явный exit code `0` при успехе и ненулевой при ошибке.
4. Логи писать в stdout/stderr в структурированном JSON-формате.
5. Проверить контейнер локально на тестовой PostgreSQL.

## 3. Kubernetes

Создать CronJob со следующими настройками:

- `schedule: "0 6 * * *"`;
- `timeZone` — явно указать бизнес-часовой пояс;
- `concurrencyPolicy: Forbid`;
- `startingDeadlineSeconds` — окно допустимого запоздалого запуска;
- `successfulJobsHistoryLimit` / `failedJobsHistoryLimit`;
- `backoffLimit` для ограниченных повторных запусков;
- `restartPolicy: Never` или `OnFailure` в соответствии с выбранной retry-моделью;
- `resources.requests/limits` для CPU/RAM;
- Secret для DB credentials;
- ServiceAccount с минимальными правами;
- NetworkPolicy, если используется в кластере.

## 4. Хранилище результата

Для production предпочтительно объектное хранилище, а не локальный filesystem Pod:

1. создать bucket/prefix для прайс-листов;
2. выдать ServiceAccount право только на необходимый bucket/prefix;
3. задать retention/versioning согласно требованиям бизнеса;
4. при необходимости формировать signed URL или публиковать ссылку через существующий B2B API.

## 5. Наблюдаемость

Минимальные метрики:

- число успешных/неуспешных Job;
- длительность Job;
- количество выгруженных строк;
- размер итогового файла;
- timestamp последнего успешного экспорта.

Логи должны содержать как минимум `job_id`, `run_date`, `client_id`, `rows_exported`, `duration_ms`, `status`, `error_code`.

Alert: к контрольному времени прайс-лист за текущий день не создан или Job завершился `Failed`.

## 6. Проверка перед production

1. Функциональный тест SQL и формата CSV.
2. Повторный запуск за одну дату — отсутствие дубликатов/частичных файлов.
3. Искусственное падение БД — проверка retry/backoff.
4. Запуск дольше одного периода — проверка `concurrencyPolicy: Forbid`.
5. Замер времени и памяти на 5k, 10k и увеличенном тестовом наборе.
6. Проверка алерта и централизованных логов.
7. Зафиксировать Runbook для ручного повторного запуска конкретной даты.
