# Верхнеуровневый план реализации задания 2

## 1. Подготовка приложения экспорта

1. Создать небольшое приложение `price-list-exporter`, не хранящее состояние между запусками.
2. Получать параметры подключения к PostgreSQL только из переменных окружения и Kubernetes Secret.
3. Использовать отдельного пользователя БД с правами только на чтение.
4. Подготовить SQL-запрос с `JOIN` по `products`, `categories`, `clients`, `client_prices`.
5. В результирующий набор обязательно включить `client_id` и отсортировать данные как минимум по `client_id`, а затем по категории и товару.
6. Читать результат потоково с использованием курсора, чтобы не загружать весь набор в память.
7. При изменении `client_id` завершать файл текущего клиента и открывать файл следующего. Это позволит получить отдельный прайс-лист на клиента без N+1 SQL-запросов.
8. CSV формировать потоково. Для XLSX использовать библиотеку, которая умеет записывать строки последовательно без хранения всей книги в памяти.
9. Для каждого файла использовать детерминированный ключ, например `price-lists/<run-date>/<client-id>/price-list.csv` или `.xlsx`.
10. Файл сначала формировать под временным именем, а после успешного завершения публиковать под итоговым ключом, чтобы клиент не увидел частичный результат.
11. Повторный запуск за ту же дату сделать идемпотентным: либо перезаписывать объект с тем же ключом, либо создавать версию и после успешной записи переключать указатель на актуальный файл.
12. После завершения проверить, что сформированы файлы для всех ожидаемых активных B2B-клиентов.

## 2. Контейнеризация

1. Подготовить Dockerfile с минимальным образом среды выполнения.
2. Запускать процесс от непривилегированного пользователя.
3. Возвращать код завершения `0` при успехе и ненулевой код при ошибке.
4. Писать логи в `stdout/stderr` в структурированном JSON-формате.
5. Не хранить итоговые файлы только во внутреннем слое контейнера. Локальный каталог можно использовать лишь как временное место формирования, если это требуется библиотеке.
6. Проверить контейнер локально на тестовой PostgreSQL.

## 3. Kubernetes CronJob

Создать CronJob со следующими настройками:

- `schedule: "0 6 * * *"`;
- `timeZone` — явно указать бизнес-часовой пояс и проверить поддержку этой настройки версией Kubernetes;
- `concurrencyPolicy: Forbid`;
- `startingDeadlineSeconds` — допустимое окно запоздалого запуска;
- `successfulJobsHistoryLimit` / `failedJobsHistoryLimit`;
- `backoffLimit` для ограниченного числа повторных запусков;
- `restartPolicy: Never` или `OnFailure` в соответствии с выбранной моделью повторов;
- `resources.requests/limits` для CPU и памяти;
- Secret для учётных данных БД;
- ServiceAccount с минимальными правами;
- NetworkPolicy, если она используется в кластере;
- `securityContext` для запуска без `root` и с минимальными привилегиями.

Перед промышленным развёртыванием отдельно проверить поведение при пересечении запусков и при временной недоступности БД или управляющего контура Kubernetes.

## 4. Хранилище результата

В промышленной среде использовать объектное хранилище, а не локальную файловую систему Pod:

1. создать bucket и отдельный префикс для прайс-листов;
2. выдать ServiceAccount доступ только к нужному bucket/prefix;
3. задать срок хранения и версионирование в соответствии с требованиями бизнеса;
4. применять детерминированную структуру ключей по дате и клиенту;
5. при необходимости формировать подписанную ссылку или публиковать ссылку через существующий B2B API;
6. не предоставлять одному клиенту доступ к каталогам других клиентов.

## 5. Наблюдаемость

Минимальные метрики:

- количество успешных и неуспешных Job;
- длительность Job;
- количество выгруженных строк;
- количество обработанных клиентов;
- количество успешно опубликованных файлов;
- размер итоговых файлов;
- время последнего успешного экспорта.

Логи должны содержать как минимум `job_id`, `run_date`, `client_id`, `rows_exported`, `files_created`, `duration_ms`, `status`, `error_code`.

Ключевые оповещения:

- Job завершился со статусом `Failed`;
- к контрольному времени нет успешного Job за текущую дату;
- сформировано меньше файлов, чем ожидается для активных B2B-клиентов;
- длительность Job заметно отклоняется от обычного значения.

## 6. Проверка перед промышленным развёртыванием

1. Функционально проверить SQL-запрос и формат CSV/XLSX.
2. Проверить корректность индивидуальной цены для разных `client_id`.
3. Убедиться, что для 100–500 клиентов не возникает N+1 SQL-запросов.
4. Повторить запуск за одну дату и убедиться в отсутствии дубликатов и частичных файлов.
5. Искусственно сделать БД недоступной и проверить повторные попытки и ненулевой код завершения.
6. Запустить задачу дольше одного периода и проверить `concurrencyPolicy: Forbid`.
7. Замерить время и память на 5 000, 10 000 и увеличенном тестовом наборе.
8. Проверить минимально достаточные `resources.requests/limits` и отсутствие `OOMKilled`.
9. Проверить централизованные логи, метрики и оповещения.
10. Подготовить инструкцию для ручного повторного запуска за конкретную дату.

## 7. Порядок внедрения

1. Реализовать приложение экспорта и SQL-запрос на тестовой БД.
2. Добавить локальную генерацию CSV, затем XLSX при необходимости.
3. Добавить публикацию в тестовое объектное хранилище.
4. Собрать Docker-образ и выполнить короткую проверку запуска.
5. Развернуть CronJob в тестовом пространстве имён с ускоренным расписанием.
6. Проверить повторные попытки, `Forbid`, наблюдаемость и идемпотентность.
7. Провести нагрузочное тестирование на объёмах задания и с запасом.
8. Зафиксировать промышленное расписание `0 6 * * *` и бизнес-часовой пояс.
9. Выпустить решение в промышленную среду с оповещением об отсутствии ежедневного успешного результата.
