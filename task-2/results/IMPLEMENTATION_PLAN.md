# Верхнеуровневый план имплементации Task 2

## 1. Подготовка экспортёра

1. Создать небольшое stateless-приложение `price-list-exporter`.
2. Получать параметры подключения к PostgreSQL только из переменных окружения/Secret.
3. Использовать отдельного read-only пользователя БД.
4. Подготовить SQL с JOIN по `products`, `categories`, `clients`, `client_prices`.
5. В результирующий набор обязательно включить `client_id` и отсортировать данные как минимум по `client_id`, а далее по категории/товару.
6. Читать результат потоково/cursor-подходом, чтобы не загружать весь набор в память.
7. При изменении `client_id` завершать writer текущего клиента и открывать writer следующего. Так можно получить отдельный кастомный файл на клиента без N+1 SQL-запросов.
8. CSV формировать потоково. Для XLSX использовать streaming/write-only API библиотеки, а не строить весь workbook в памяти.
9. Для каждого файла использовать детерминированный ключ, например `price-lists/<run-date>/<client-id>/price-list.csv` или `.xlsx`.
10. Файл сначала формировать под временным именем/ключом, а после успешного завершения атомарно публиковать финальный объект, чтобы потребитель не увидел частичный результат.
11. Повторный запуск за ту же дату сделать идемпотентным: либо перезаписывать объект с тем же ключом, либо писать версионированный объект и атомарно обновлять указатель на актуальную версию.
12. После завершения проверить, что сформированы файлы для всех ожидаемых активных B2B-клиентов.

## 2. Контейнеризация

1. Подготовить Dockerfile с минимальным runtime-образом.
2. Запускать процесс от непривилегированного пользователя.
3. Добавить явный exit code `0` при успехе и ненулевой при ошибке.
4. Логи писать в stdout/stderr в структурированном JSON-формате.
5. Не хранить итоговые файлы только в writable-layer контейнера: локальный каталог использовать исключительно как временное место формирования, если это необходимо библиотеке.
6. Проверить контейнер локально на тестовой PostgreSQL.

## 3. Kubernetes CronJob

Создать CronJob со следующими настройками:

- `schedule: "0 6 * * *"`;
- `timeZone` — явно указать бизнес-часовой пояс и проверить поддержку версией Kubernetes;
- `concurrencyPolicy: Forbid`;
- `startingDeadlineSeconds` — окно допустимого запоздалого запуска;
- `successfulJobsHistoryLimit` / `failedJobsHistoryLimit`;
- `backoffLimit` для ограниченных повторных запусков;
- `restartPolicy: Never` или `OnFailure` в соответствии с выбранной retry-моделью;
- `resources.requests/limits` для CPU/RAM;
- Secret для DB credentials;
- ServiceAccount с минимальными правами;
- NetworkPolicy, если используется в кластере;
- securityContext для запуска без root и с минимальными привилегиями.

Перед production отдельно проверить поведение при пересечении запусков и при временной недоступности control plane/БД.

## 4. Хранилище результата

Для production использовать объектное хранилище, а не локальный filesystem Pod:

1. создать bucket/prefix для прайс-листов;
2. выдать ServiceAccount право только на необходимый bucket/prefix;
3. задать retention/versioning согласно требованиям бизнеса;
4. применять детерминированную структуру ключей по дате и клиенту;
5. при необходимости формировать signed URL или публиковать ссылку через существующий B2B API;
6. не предоставлять клиенту доступ к префиксам других клиентов.

## 5. Наблюдаемость

Минимальные метрики:

- число успешных/неуспешных Job;
- длительность Job;
- количество выгруженных строк;
- количество обработанных клиентов;
- количество успешно опубликованных файлов;
- размер итоговых файлов;
- timestamp последнего успешного экспорта.

Логи должны содержать как минимум `job_id`, `run_date`, `client_id`, `rows_exported`, `files_created`, `duration_ms`, `status`, `error_code`.

Ключевые алерты:

- Job завершился `Failed`;
- к контрольному времени нет успешного Job за текущую дату;
- сформировано меньше файлов, чем ожидается для активных B2B-клиентов;
- длительность Job существенно отклоняется от baseline.

## 6. Проверка перед production

1. Функциональный тест SQL и формата CSV/XLSX.
2. Проверка корректности индивидуальной цены для разных `client_id`.
3. Проверка, что для 100–500 клиентов не возникает N+1 SQL-запросов.
4. Повторный запуск за одну дату — отсутствие дубликатов и частичных файлов.
5. Искусственное падение БД — проверка retry/backoff и ненулевого exit code.
6. Запуск дольше одного периода — проверка `concurrencyPolicy: Forbid`.
7. Замер времени и памяти на 5k, 10k и увеличенном тестовом наборе.
8. Проверка минимальных resource requests/limits и отсутствия OOM.
9. Проверка централизованных логов, метрик и алертов.
10. Зафиксировать Runbook для ручного повторного запуска конкретной даты.

## 7. Порядок внедрения

1. Реализовать exporter и SQL на тестовой БД.
2. Добавить локальную генерацию CSV, затем XLSX при необходимости.
3. Добавить публикацию в тестовый bucket.
4. Собрать Docker-образ и выполнить smoke-test.
5. Развернуть CronJob в dev namespace с ускоренным тестовым расписанием.
6. Проверить retries, `Forbid`, observability и идемпотентность.
7. Провести нагрузочный тест на объёмах задания и с запасом.
8. Зафиксировать production schedule `0 6 * * *` и бизнес-таймзону.
9. Выпустить в production с алертом на отсутствие ежедневного успешного результата.
