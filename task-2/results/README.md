# Task 2. Дизайн модуля пакетной обработки прайс-листов

## Исходные условия

Каждое утро ровно в **06:00** требуется связать данные PostgreSQL (`products`, `categories`, `clients`, `client_prices`) и сформировать кастомные CSV/XLS-прайс-листы для B2B-клиентов.

Объём одной выгрузки — порядка **5 000–10 000 строк**. Дополнительной сложной обработки, ветвлений и ML нет. Инфраструктура уже облачная и микросервисная.

## Сравнение вариантов

> В колонке **K8s Job** рассматривается связка **Kubernetes CronJob → Job → Pod**, поскольку именно CronJob добавляет требуемое расписание.

| Критерий | Spring Batch | Apache Airflow | K8s Job / CronJob | Spark |
|---|---|---|---|---|
| Наличие CRON-расписания | Сам Spring Batch — нет; нужен Scheduler/Quartz/CronJob/SCDF | Да, встроенное расписание DAG | **Да, встроено в CronJob** | Нет, нужен внешний scheduler/orchestrator |
| Сложность реализации логики | Средняя; для простой выгрузки избыточная структура Job/Step/Reader/Writer | Средняя/высокая; DAG из одной простой задачи избыточен | **Низкая**: один контейнер с SQL + CSV export | Высокая для 5–10 тыс. строк, неоправданно |
| Ресурсоёмкость | Средняя: JVM + приложение | Высокая: scheduler, webserver, metadata DB и executor | **Низкая**: pod живёт только во время выгрузки | Высокая: driver/executors/cluster overhead |
| Масштабируемость | Хорошая, но partitioning требует настройки | Отличная для множества DAG/tasks | Достаточная; можно задать ресурсы/parallelism, но здесь не требуется | Отличная для больших данных, но масштаб лишний |
| Развёртывание в облаке и интеграция | Хорошо для Java-экосистемы | Хорошо, но больше инфраструктуры | **Отлично**, нативно для Kubernetes/облака | Сложнее и дороже |
| Логи и мониторинг | Actuator/Micrometer + централизованные логи | Встроенный UI + внешние метрики | **Хорошо интегрируется** с Kubernetes logs, Prometheus/Grafana/ELK | Хорошо, но требует отдельного стека |

## Решение

Выбран **Kubernetes CronJob**.

Причины:

1. Задача выполняется строго раз в сутки и не содержит сложного workflow.
2. Объём 5–10 тыс. строк мал для Spark и не оправдывает отдельный Airflow/SCDF.
3. CronJob не требует постоянно работающего сервиса: ресурсы потребляются только во время выполнения.
4. `concurrencyPolicy: Forbid` предотвращает наложение двух ежедневных запусков.
5. `startingDeadlineSeconds`, `backoffLimit`, history limits и `restartPolicy` позволяют задать предсказуемое поведение при сбоях.
6. В облаке контейнер можно запустить в существующем Kubernetes-кластере, секреты вынести в Kubernetes Secret/Secret Manager, а CSV складывать в объектное хранилище.

Spring Batch здесь технически возможен, но для одной SQL-выгрузки добавляет лишнюю сложность. Airflow оправдан, когда появятся зависимости, ветвления, десятки пайплайнов или разнородные внешние системы. Spark для такого объёма данных не нужен.

## Как работает To Be

1. В 06:00 CronJob создаёт Kubernetes Job.
2. Job запускает одноразовый Pod с контейнером `price-list-exporter`.
3. Экспортёр открывает read-only соединение с PostgreSQL.
4. Одним SQL-запросом получает необходимые данные с JOIN по таблицам `products`, `categories`, `clients`, `client_prices`.
5. Результат потоково записывается в CSV, чтобы не держать весь набор в памяти.
6. В production файл загружается в объектное хранилище (например, GCS). Имя включает дату запуска и/или идентификатор клиента.
7. Контейнер завершается кодом `0`; Kubernetes помечает Job как `Succeeded`.
8. При ошибке Job выполняет повторные попытки в пределах `backoffLimit`. Новый ежедневный запуск не стартует одновременно с предыдущим благодаря `concurrencyPolicy: Forbid`.
9. Логи контейнера собираются централизованно, метрики Kubernetes/Job — Prometheus/Grafana.

Исходник диаграммы: `c4-to-be.puml`.
