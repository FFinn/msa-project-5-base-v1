# Задание 2. Дизайн модуля пакетной обработки прайс-листов

## Результаты задания

## Исходные условия

Каждое утро ровно в **06:00** требуется связать данные PostgreSQL:

- `products` — ~5 000–10 000 строк;
- `categories` — ~50–200 строк;
- `clients` — ~100–500 строк;
- `client_prices` — ~10 000–20 000 строк.

Результат — индивидуальные CSV/XLS-прайс-листы для B2B-клиентов. Объём одной выгрузки — порядка **5 000–10 000 строк**. Дополнительной сложной обработки, ветвлений, машинного обучения или распределённых вычислений не требуется. Инфраструктура уже облачная и микросервисная.

## Выбранное решение

**Kubernetes CronJob** лучше всего соответствует текущей задаче:

1. запуск требуется строго один раз в сутки в 06:00;
2. процесс фактически состоит из одной простой операции экспорта;
3. объём данных не оправдывает Apache Spark;
4. Apache Airflow и Spring Batch добавляют платформенную сложность, которая здесь не нужна;
5. CronJob естественно встраивается в существующую Kubernetes-инфраструктуру и не требует отдельного постоянно работающего планировщика приложения;
6. `concurrencyPolicy`, `startingDeadlineSeconds`, `backoffLimit`, ограничения истории запусков и код завершения процесса дают предсказуемое поведение при сбоях.

Полное обоснование и сравнительная таблица находятся в `ADR-002-b2b-price-list-batch-processing.md`.

## Контекстная C4-диаграмма целевого состояния

![Контекстная C4-диаграмма](c4-context-to-be.png)

На контекстной диаграмме выделен отдельный программный модуль **«Модуль формирования B2B-прайс-листов»**.

Он взаимодействует с:

- **онлайн-магазином** — получает актуальные данные товаров, категорий, клиентов и индивидуальных цен из PostgreSQL;
- **объектным хранилищем** — публикует готовые CSV/XLS;
- **B2B-клиентом** — предоставляет доступ к сформированному прайс-листу.

Kubernetes на контекстной C4-диаграмме сознательно не изображается как отдельная бизнес-система: это инфраструктурная деталь развёртывания. Она показана на дополнительной контейнерной диаграмме через цепочку `Kubernetes CronJob → Job → Pod`.

## Как работает решение

1. Kubernetes CronJob с расписанием `0 6 * * *` в заданном `timeZone` создаёт `Job`.
2. `Job` запускает одноразовый `Pod` с контейнером `price-list-exporter`.
3. Приложение экспорта открывает соединение с PostgreSQL только для чтения.
4. SQL-запрос с `JOIN` связывает `products`, `categories`, `clients`, `client_prices` и возвращает данные, отсортированные по `client_id`.
5. Результат читается потоково. При смене `client_id` завершается файл текущего клиента и начинается файл следующего. Это позволяет избежать N+1-запросов и не держать весь набор в памяти.
6. CSV записывается потоково; для XLSX используется библиотека с режимом последовательной записи без хранения всей книги в памяти.
7. Каждый файл сначала создаётся как временный объект и только после успешного формирования публикуется под итоговым детерминированным ключом, например `price-lists/<run-date>/<client-id>/price-list.csv`.
8. В промышленной среде результат сохраняется в объектное хранилище, например Google Cloud Storage или S3-совместимое хранилище, а не на локальную файловую систему Pod.
9. При успехе процесс завершается кодом `0`, после чего Kubernetes помечает Job как `Succeeded`.
10. При ошибке Kubernetes выполняет ограниченное число повторных запусков в пределах `backoffLimit`; `concurrencyPolicy: Forbid` не позволяет очередному ежедневному запуску пересечься с предыдущим.
11. Логи контейнера собираются централизованно; состояние и длительность Job контролируются через Kubernetes, Prometheus и Grafana.
