# ADR-001. Выбор платформы для пакетной обработки данных

- **Статус:** принято
- **Автор:** Александр Вафин
- **Дата:** 2026-09-07
- **Контекст:** проектная работа 5 спринта, задание 1

## 1. Контекст

Маркетинговому отделу требуется пакетная обработка клиентских и заказных данных из нескольких источников:

- CSV-файлов со статусами доставок;
- PostgreSQL с заказами, платежами и расширенными данными пользователей;
- Apache Kafka с событиями изменения заказов;
- внешних API.

В дальнейшем процесс должен уметь работать с BigQuery, Amazon Redshift, Apache Kafka и Apache Spark. Нужны условия и ветвления, повторные попытки отдельных шагов, резервные сценарии после ошибок, уведомления и понятное наблюдение за состоянием выполнения.

Ожидаемый объём одного запуска — около **1 млн записей**. При этом оркестратор не должен сам становиться местом хранения и передачи всего набора данных: его задача — управлять процессом, а тяжёлую обработку должны выполнять специализированные системы.

Для проектной работы также требуется показать локально развёрнутый прототип, который можно без смены подхода перенести в облачную инфраструктуру.

## 3. Рассмотренные варианты

### 3.1. Apache Airflow

**Преимущества**

- процесс описывается на Python как DAG — направленный ациклический граф;
- зависимости и параллельные ветки задаются явно;
- есть `BranchPythonOperator` и правила запуска `TriggerRule`;
- повторные попытки задаются на уровне отдельной задачи;
- есть веб-интерфейс, история запусков и журналы задач;
- существует большое количество готовых пакетов интеграции с облачными сервисами и системами обработки данных;
- хорошо подходит для процессов, в которых участвуют разные технологии.

**Недостатки**

- требуется отдельная инфраструктура Airflow: планировщик, база метаданных, механизм выполнения задач и веб-интерфейс;
- для одной простой независимой задачи по расписанию Airflow был бы избыточен;
- Airflow не является системой потоковой обработки с миллисекундной задержкой.

### 3.2. Spring Batch + Spring Cloud Data Flow

**Преимущества**

- удобная пакетная обработка порциями;
- состояние выполнения хранится в `JobRepository`;
- есть повторные попытки и пропуск некорректных элементов;
- хорошо сочетается с Java и Spring;
- Spring Cloud Data Flow добавляет централизованное управление заданиями.

**Почему не выбран**

В данном задании основная сложность связана не с обработкой одной Java-задачи, а с координацией разнородных внешних систем. Для BigQuery, Amazon Redshift, Apache Spark, Apache Kafka и внешних API в Airflow уже существует развитая экосистема операторов и соединений. В Spring Batch такую оркестрацию пришлось бы в большей степени собирать самостоятельно.

### 3.3. Kubernetes CronJob

**Преимущества**

- простое развёртывание контейнеризованной задачи по расписанию;
- можно задать `concurrencyPolicy`, ограничения повторных запусков и ресурсов.

**Почему не выбран**

CronJob хорошо запускает один контейнер, но не даёт полноценного графа зависимостей, ветвлений и состояния многошагового процесса. Эти механизмы пришлось бы реализовывать самостоятельно.

### 3.4. Apache Spark

**Преимущества**

- эффективная распределённая обработка больших объёмов данных;
- подходит для тяжёлых преобразований и агрегаций.

**Почему не выбран**

Apache Spark — вычислительный движок, а не оркестратор всего процесса. Он может быть одним из шагов, но сам по себе не решает задачу управления зависимостями, уведомлениями, внешними API и ветвлениями.

## 4. Решение

Для задания выбран **Apache Airflow** как оркестратор пакетной обработки.

Airflow не будет обрабатывать миллион записей внутри XCom или базы метаданных. Его роль — определить порядок действий, запустить нужные системы и проконтролировать результат. Большие наборы данных остаются в PostgreSQL, BigQuery, Amazon Redshift, Apache Spark или объектном хранилище, а между задачами Airflow передаются только небольшие служебные значения, идентификаторы и ссылки на данные.

Такой подход закрывает функциональные требования ФТ-01…ФТ-08 и одновременно не нарушает НФТ-03.

## 5. Интеграции

### 5.1. BigQuery

Для Google Cloud существует пакет `apache-airflow-providers-google`. В нём есть готовые операторы и средства подключения к BigQuery и другим сервисам Google Cloud. Это позволяет выполнять запросы и задания BigQuery как отдельные шаги DAG без написания собственного механизма оркестрации.

### 5.2. Amazon Redshift

Для сервисов AWS используется пакет `apache-airflow-providers-amazon`. Он содержит готовые средства работы с Amazon Redshift и другими сервисами AWS. Выполнение SQL или загрузка данных оформляются как отдельные задачи DAG.

### 5.3. Apache Kafka

Для Apache Kafka доступен пакет `apache-airflow-providers-apache-kafka`.

Kafka может использоваться как источник данных или как источник события для запуска пакетного процесса. Для запуска по событию предпочтительно, чтобы отдельный потребитель получил сообщение Kafka и вызвал REST API Airflow. Если допустимо ожидание внутри DAG, можно использовать сенсор.

Airflow при этом не заменяет Kafka и Apache Flink в сценариях непрерывной потоковой обработки.

### 5.4. Apache Spark

Airflow поддерживает запуск заданий Spark, в том числе через `SparkSubmitOperator`. В этой схеме Airflow отвечает за порядок и зависимости, а Apache Spark выполняет тяжёлые вычисления.

### 5.5. Внешние API

HTTP-вызовы можно оформить отдельными задачами Airflow через готовые HTTP-операторы или Python-задачи. Для каждого такого шага отдельно задаются повторные попытки, ограничение времени выполнения и журналирование.

## 6. Ветвление, условия и запуск по событию

Для ФТ-03 в прототипе используется `BranchPythonOperator`. Он выбирает одну из веток, а невыбранная помечается Airflow как `skipped`.

Для объединения веток и аварийных сценариев используются штатные правила `TriggerRule`, например:

- `all_success`;
- `one_failed`;
- `one_success`;
- `none_failed_min_one_success`.

Для ФТ-07 Airflow может запускать DAG по расписанию либо по внешнему вызову REST API. Для событий Kafka или вебхуков целевая схема выглядит так:

```text
Apache Kafka / вебхук → сервис-получатель события → REST API Airflow → запуск DAG
```

Так Airflow остаётся оркестратором пакетного процесса и не превращается в брокер событий.

## 7. Повторные попытки, резервный сценарий и уведомления

Для ФТ-04 повторные попытки задаются на уровне задачи параметрами Airflow:

- `retries`;
- `retry_delay`;
- `retry_exponential_backoff`;
- `max_retry_delay`.

Для ФТ-05 отдельного «оператора резервного сценария» не требуется. После исчерпания попыток задача получает состояние `failed`, после чего задача с `TriggerRule.ONE_FAILED` может выполнить аварийное действие.

Для ФТ-06 используются `EmailOperator` или функции обратного вызова `on_failure_callback` и `on_success_callback`. В локальном прототипе SMTP-сервер имитируется MailHog.

## 8. Наблюдаемость

НФТ-01 и НФТ-06 закрываются штатными средствами Airflow:

- веб-интерфейсом;
- представлением Graph/Grid;
- состояниями отдельных задач;
- историей запусков DAG;
- журналами задач;
- сведениями о повторных попытках и ошибках;
- базой метаданных Airflow.

В промышленной среде метрики и логи Airflow дополнительно должны поступать в общую систему наблюдаемости компании.

## 9. Развёртывание в облаке

Для Google Cloud предпочтителен **Cloud Composer**, то есть управляемый Apache Airflow. Он снижает объём ручного сопровождения и хорошо интегрируется с IAM, BigQuery и Google Cloud Storage.

Альтернативный вариант — собственный Airflow в Kubernetes/GKE. В таком случае разворачиваются:

- Scheduler;
- Webserver;
- отказоустойчивая PostgreSQL как база метаданных;
- `KubernetesExecutor` или `CeleryExecutor`;
- рабочие процессы или отдельные Pod;
- доставка DAG через Git и CI/CD;
- Kubernetes Secret или Secret Manager;
- централизованный сбор логов, метрик и оповещений.

Для тяжёлых задач `KubernetesExecutor` позволяет запускать отдельную задачу в отдельном Pod и назначать ей собственные ограничения CPU и памяти.

## 10. Масштабирование

Само число «1 млн строк» ещё не означает, что требуется Apache Spark. Выбор зависит от размера строки, сложности преобразований и допустимого времени выполнения.

Начальный вариант для текущего объёма:

1. выполнять массовые операции средствами PostgreSQL, BigQuery или Amazon Redshift;
2. не передавать большие наборы через XCom;
3. хранить промежуточные результаты во внешнем хранилище;
4. подключать Apache Spark только для действительно тяжёлых распределённых преобразований.

## 11. Последствия решения

### Положительные

- требования ФТ-01…ФТ-08 закрываются штатными средствами Airflow и его пакетами интеграции;
- процесс становится видимым и управляемым;
- отдельные шаги можно повторять независимо;
- тяжёлые вычисления остаются в системах, которые для этого предназначены;
- локальный прототип и облачный вариант используют одну и ту же модель DAG.

### Отрицательные и нейтральные

- появляется отдельная платформа, которую нужно сопровождать;
- команде необходимо понимать модель DAG, Scheduler, Executor и базу метаданных;
- для простой одиночной задачи Airflow был бы неоправданно сложным;
- запуск по событию через Kafka требует отдельного получателя события или сенсора.

## 12. Риски и ограничения

1. Нельзя передавать большие наборы данных через XCom.
2. База метаданных Airflow является критичной частью платформы и должна быть отказоустойчивой.
3. Большое число сенсоров в режиме постоянного опроса может занимать рабочие слоты; для длительного ожидания нужно использовать подходящий режим сенсора.
4. Производительность процесса должна подтверждаться нагрузочным тестом на данных, близких к реальным.
5. Airflow не следует использовать как систему непрерывной потоковой обработки.

## 13. Когда решение стоит пересмотреть

ADR следует пересмотреть, если процесс станет одной простой независимой задачей по расписанию — тогда Kubernetes CronJob будет проще. Обратная ситуация тоже возможна: если основной объём работы превратится в непрерывную обработку событий с малой задержкой, оркестрацию нужно будет дополнить или заменить специализированной потоковой платформой.
